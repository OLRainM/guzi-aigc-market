# 谷子交易平台与 3D 能力：技术分析

## 本地启动

第一阶段工程位于 `apps/web`、`apps/api` 和 `apps/worker`，基础设施由根目录的 `docker-compose.yml` 统一编排。

```powershell
Copy-Item .env.example .env
docker compose up --build
```

启动后可访问：

- Web：`http://localhost:5173`（可注册、登录、发布商品并上传图片/GLB）
- 同源 API 健康检查：`http://localhost:5173/healthz`、`http://localhost:5173/readyz`
- MinIO 控制台：`http://localhost:9001`（仅本机访问）

服务器部署时在 `.env` 中设置 `WEB_PORT=80`，并在防火墙中开放 TCP 80，即可通过 `http://<服务器公网IP>` 直接访问。前端通过同一 IP 下的 `/api/` 调用 API，无需域名、DNS、TLS 证书或额外跨域配置；MySQL、Redis、MinIO、API 和 Worker 端口应仅绑定 `127.0.0.1` 或保持在 Compose 内部网络。

开发环境默认凭据仅用于本地联调，部署前必须通过环境变量替换。MySQL、Redis 和 MinIO 使用 Docker 数据卷持久化，`docker compose down` 不会删除数据；不要在保留数据时使用 `docker compose down -v`。

Redis Streams 最小链路可通过下列命令验证：

```powershell
docker compose exec redis redis-cli XADD generation_jobs * job_id test-job job_type health_check message hello
docker compose logs worker
```

## 当前 AI 生成主流程

MVP 的核心演示链路为：

```text
用户输入文本 → RAG 检索领域知识 → Prompt 优化与结构化参数提取
→ 用户确认 → 异步调用文本生成 3D 模型 → 保存 GLB → 网页预览/发布商品
```

首版优先验证流程完整性，生成模型只需能够正常加载、旋转和查看，不要求完全还原真实商品。无第三方 AI 凭据时使用 Mock Provider，避免外部服务阻塞开发；参考图片输入作为后续增强能力。

## 技术栈优化结论

| 层级 | 推荐方案 | 调整说明 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite + React Router + Zustand + Tailwind CSS | 保留一天 MVP 的快速交付能力，统一路由、状态和样式方案 |
| 业务后端 | Go + Gin + GORM | 从“可选后端”提升为第二阶段主线，承载用户、资产、交易、订单和权限 |
| AI 服务 | Python + FastAPI + RAG + 文本生成 3D Provider Adapter | 独立 AI Service，先优化用户文本，再屏蔽第三方 3D 模型服务差异，支持异步任务与后续自托管 |
| 数据库 | MySQL 8 | 作为订单、库存、支付流水和账本的最终一致性来源 |
| 缓存与任务 | Redis + Redis Streams（MVP）/ RabbitMQ（扩展） | 先减少基础设施数量，后续按任务量切换专业消息队列 |
| 文件存储 | MinIO（本地）/ OSS、COS 或 S3（线上） | 图片、GLB、源文件和生成结果统一对象存储 |
| 支付 | 支付宝沙箱 → 正式支付/合规分账 | 演示期只模拟，生产期必须验签、幂等和金额校验 |
| 物流 | 模拟物流 → 单一物流适配器 | 避免首版引入多物流聚合复杂度 |
| 部署与观测 | Docker Compose；OpenTelemetry + Prometheus + Grafana | 先保证可复现部署和关键链路可观测 |

## 1. 项目本质

图片中的项目不是单一的 3D 展示网站，而是五类系统的组合：

1. AIGC 任务平台：提交提示词或图片，异步生成 3D 模型。
2. 3D 数字资产平台：上传、预览、存储、下载和版本管理模型。
3. 双边交易市场：出售模型、发布悬赏、投稿竞标、确认交付。
4. 订单与支付平台：订单状态机、支付回调、退款、结算和分账。
5. 物流履约平台：实物打印件或周边商品的发货、轨迹和签收。

真正困难的部分不是页面，而是异步 AI 任务、交易状态一致性、支付安全、3D 文件处理和平台合规。

### 用户与交易身份

平台采用统一账户体系，买家、卖家和创作者是可重叠的业务身份：同一用户既可以买，也可以卖，还可以创建 AI 建模任务。卖家分为发布二手闲置的个人卖家和发布全新商品的厂家卖家；创作者同样可以兼具任一卖家身份。管理员使用独立授权角色。

## 2. 推荐的总体架构

课程设计、毕业设计或简历项目不建议一开始拆成大量微服务。推荐先做“模块化单体 + 独立 AI Worker”，需要扩容时再按业务边界拆服务。

```text
Web / Mobile
    |
    v
Go API (Gin)
    |-- 用户与权限
    |-- 资产与文件存储
    |-- 商品与内容发布
    |-- 出售与悬赏
    |-- 订单与支付
    |-- 物流与通知
    |
    |-- MySQL：核心交易数据
    |-- Redis：缓存、幂等键、分布式锁、限流
    |-- MinIO/COS/S3：图片、视频、GLB、参考图和生成结果
    |-- MQ：AI 生成、转码、缩略图、通知任务
    |
    v
Python AI Worker / 第三方 AIGC API
    |-- Replicate / Tripo AI 等托管 API
    |-- TripoSR 等自托管模型（需要 GPU）
```

| 领域 | 推荐技术 | 用途 |

| 消息队列 | RabbitMQ / NATS JetStream | AI 生成、模型转换、通知等异步任务 |
| 对象存储 | MinIO（本地）/ OSS、COS、S3（线上） | 模型、贴图、封面和交付文件 |

## 4. 3D 与 AIGC 专项技术

### 模型格式和 Web 展示

- Web 端优先使用 `glTF/GLB`，不直接把 OBJ、FBX 当作主要交付格式。
- 使用 Blender CLI 或 Assimp 做格式转换、网格检查和缩略图渲染。
- 使用 Draco 压缩几何数据，KTX2/Basis 压缩纹理，减少加载时间。
- 保存原文件、标准化 GLB、封面图和元数据，不覆盖用户原始文件。
- 对多边形数量、纹理尺寸、骨骼动画、文件大小设置明确限制。

### AI 任务流程

AI 生成必须做成异步任务，不能让 HTTP 请求一直等待模型返回：

```text
创建任务 -> 入队 -> AI Worker 调用模型/API -> 下载结果
        -> 格式校验/转换 -> 上传对象存储 -> 更新任务状态 -> 通知前端
```

任务至少需要 `PENDING/RUNNING/SUCCEEDED/FAILED/CANCELED` 状态、重试次数、超时、错误原因、模型版本和计费信息。第三方回调必须验签并保证幂等。

### 自托管还是调用 API

- MVP：调用 Replicate、Tripo AI 等托管 API，开发速度最快。
- 需要成本控制或数据私有化时：再部署 TripoSR 等开源模型。
- 自托管需要 NVIDIA GPU、CUDA、显存评估、模型队列、批处理和 GPU 监控，运维复杂度明显更高。

## 5. 交易、支付和订单设计

### 双边交易

- `FOR_SALE`：卖家发布固定价作品，买家购买。
- `WANTED`：买家发布悬赏，创作者投稿或报价，买家选稿后进入交付。
- 出售、悬赏、投稿、订单必须是不同的数据实体，不要用一张大表承载所有状态。
- 所有状态迁移由服务端校验，例如已取消订单不能再次支付，未中标投稿不能交付。

### 三层状态机

建议分开维护：

1. 资产/展示状态：草稿、审核中、已发布、已下架。
2. 交易订单状态：待支付、已支付、制作/交付中、待验收、已完成、已取消、退款中、已退款。
3. 物流状态：待发货、运输中、已签收、异常。

状态变化写入事件表或操作日志。关键迁移使用数据库事务和乐观锁，库存扣减使用条件更新；Redis 只能辅助，不能替代数据库最终约束。

### 支付与分账

- 金额必须使用整数分或高精度 Decimal，禁止使用浮点数。
- 支付回调需要验签、幂等、金额与商户订单校验。
- 建立不可随意修改的支付流水和资金账本，退款不能只改订单状态。
- “平台 20%、创作者 80%”不能仅靠普通转账模拟。真实上线应使用支付宝合规的分账/结算产品，并确认平台是否具备相应资质。
- 学习项目可以使用支付宝沙箱和模拟分账，但文档中必须明确这不是生产资金托管方案。

## 6. 核心数据模型

最少需要以下表或聚合：

- `users`、`roles`、`user_roles`
- `assets`、`asset_files`、`asset_versions`
- `generation_jobs`、`generation_outputs`
- `sale_listings`
- `bounties`、`bounty_submissions`
- `orders`、`order_items`、`order_events`
- `payment_transactions`、`refunds`、`ledger_entries`
- `shipments`、`shipment_events`
- `notifications`、`audit_logs`

订单号、支付平台交易号、AI 第三方任务号必须有唯一索引。常用列表查询应建立组合索引，并避免 GORM 的 N+1 查询。

## 7. 安全与合规

- JWT 建议使用短期 Access Token + 可撤销 Refresh Token，并加入 RBAC 权限控制。
- 上传文件要校验扩展名、MIME、文件头、大小和压缩包内容，避免路径穿越与压缩炸弹。
- 私有模型使用签名 URL 下载，禁止把对象存储永久公网开放。
- 对支付、退款、选稿、交付等高风险接口做幂等、审计和频率限制。
- AIGC 内容需要做违规内容审核，并保留生成模型、提示词、用户确认和版权声明。
- 平台上线前要评估数字资产版权、消费者退款、隐私、内容审核、发票和平台分账资质。

## 8. 推荐 MVP 范围

第一版只做一条可以完整演示的闭环：

1. 注册登录与创作者主页。
2. 上传 GLB，浏览器内预览并发布作品。
3. 输入提示词或上传图片，调用一个第三方 API 异步生成 3D 模型。
4. 固定价购买，使用支付宝沙箱完成支付回调。
5. 简化版悬赏：发布、投稿、选稿、交付、验收。
6. 订单状态机、操作日志和站内通知。
7. 物流先使用模拟数据；确实有实体打印业务后再接一家服务商。

暂时不要做：多 AI 厂商智能路由、真实资金托管、多物流聚合、复杂竞价、Kubernetes、多区域容灾。它们会显著拖慢首个可运行版本。

## 9. 三种建设方案

### 方案 A：课程/简历演示版（推荐起点）

- 架构：React + Go 单体 + MySQL + Redis + MinIO + 第三方 AI API。
- 支付：支付宝沙箱；物流：模拟或单一接口。
- 人力：1-2 人。
- 周期：约 6-10 周，取决于 3D 前端和支付经验。
- 优点：能展示完整业务闭环，部署和调试成本可控。

### 方案 B：可试运营版

- 在方案 A 上增加消息队列、独立 Worker、内容审核、退款账本、对象存储 CDN、监控告警和正式支付能力。
- 人力：3-5 人。
- 周期：约 3-6 个月。
- 风险：支付分账、版权审核、AI 成本和售后流程。

### 方案 C：生产级平台

- 按用户、资产、交易、支付、AI、物流边界拆服务，引入 Kubernetes、服务治理、灾备和完整风控。
- 人力：通常至少 6-10 人，且需要产品、设计、测试、运维和法务支持。
- 周期：6-12 个月以上。
- 不适合作为第一版直接开工。

## 10. 建议的开发顺序

1. 先画数据库 ER 图和三层状态机，锁定业务规则。
2. 完成用户、资产上传、对象存储和 Three.js 预览。
3. 完成 AI 异步任务链路，再补超时、重试和失败恢复。
4. 完成出售/悬赏和订单状态机。
5. 接支付宝沙箱，重点测试重复回调、退款和金额校验。
6. 接物流/通知，最后补监控、压测、安全测试和部署脚本。

## 11. 最关键的技术判断

- Go 适合交易 API 和高并发服务；AI 推理仍应放在 Python 服务中。
- 首版应选择模块化单体，而不是为了简历描述强行上微服务。
- Redis 不负责最终交易一致性，MySQL 事务、唯一约束和账本才是底线。
- 3D 文件处理和异步 AI 任务是本项目区别于普通商城的核心技术亮点。
- 真正上线的最大风险往往不是性能，而是支付分账、内容版权和售后责任。
